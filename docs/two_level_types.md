## Follow-up checks and interpretation (2026-10-22)

**Run note.** The first run crashed (segfault in `libomp`): PyTorch and scikit-learn each load an OpenMP
runtime on macOS. Rerunning with `OMP_NUM_THREADS=1` fixed it. **Rule note:** no k satisfied the pre-written
rule (k = 4-8 all contain a ~2% school-day type, below the 3% minimum). The fallback coded in the script
before running (most stable k) chose k = 5. The 2% type is meaningful (school days), so the 3% minimum was too
strict for this question.

**Level 1: composition types are real and stable** (bootstrap ARI 0.93). The automatic labels are readable
but imperfect; type 1 is really a "home and chores" day (household 248 min, caregiving 73, shopping 52):

| Type | Share | Day |
| --- | ---: | --- |
| 3 | 33% | leisure day (555 min leisure, long sleep, 62% weekend) |
| 1 | 32% | home & chores day (household, caregiving, shopping) |
| 2 | 27% | work day (506 min work, 84% weekday) |
| 0 | 5% | religious / volunteer day (246 min "other", 69% weekend) |
| 4 | 2% | school day (407 min education) |

**Level 2: timing within types is continuous for the bulk of days.**
- HDBSCAN found no dense cores in any type, on either the VAE rhythm axes or engineered timing features,
  as with matched Gaussian nulls.
- Dip tests p ≈ 0.99 in every type.

**Positive control** (same HDBSCAN settings, n = 2,231):
- 3 Gaussian blobs separated by 6 / 4 / 3 / 2 SD → 3 / 3 / 2 / 0 cores; a single Gaussian → 0 cores.
- So "no cores" rules out *well-separated* timing clusters (≳ 3 SD), not heavily overlapping ones.
- The dip test is insensitive to small minority modes: an 87 / 9 / 4% day / evening / night mixture gives
  p = 0.96. It cannot rule out shift types.

**Shift work (work-day type), checked with sensitive tools on the real work-centre time:**
- **Night work is a real, distinct group, but small.** A 3-component mixture is strongly preferred over one
  component (BIC gain 1,572 vs ≤ −49 for Gaussian nulls). Components:
  - 78% day work (centre 12.2 h, SD 1.2);
  - 19% broad later/variable work (14.4 h, SD 3.7), a tail rather than a type;
  - **3% night work (centred ~midnight, SD 2.2), about 12 h from the day peak.**
- HDBSCAN on work-centre time alone shows narrow peaks at conventional hours (11:00, 12:00, 12:30, 13:00,
  13:30): standard shift conventions, real but mundane.
- **The VAE encodes night work almost perfectly** (logistic probe on the full 16-d timing latent, validation
  AUC 0.998-0.999 for three independent models). But in neither the 3 rhythm axes nor the full latent do
  night-work days form a density core. They lie along a clear direction, not in a dense clump, so
  unsupervised clustering cannot surface them.

## Conclusion

- **Schedule types exist mainly in composition** (what a day is spent on): five stable types.
- **Within each type, timing is a continuum** for nearly all days.
- **Rare but real timing types exist** (night work, ~3-4% of work days). The model represents them clearly,
  but generic clustering misses them because they are small and spread out.
- **To find and describe such types, use targeted, interpretable definitions** (e.g. work centred
  21:00-06:00) or supervised probes on the timing latent, not unsupervised clustering.

Limitations: 2022 only (development); unweighted; days, not people; one composition feature set; HDBSCAN
settings fixed before running (min cluster size 5%), with the 30-day follow-up added after seeing that the
5% size excluded small groups.
