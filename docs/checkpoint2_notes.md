# Checkpoint 2 notes: baselines

Numbers come from `docs/baselines_report.md` (run `outputs/checkpoint2/20261019-184825`), which is
generated by `scripts/run_baselines.py`. Earlier run folders from the same day are superseded debugging
runs. Data: 2022 train (6,509) and validation (1,627), unweighted. 2023 has not been used.

## What was built

| Baseline | Features | Dims |
| --- | --- | ---: |
| `totals` | share of the day in each of 13 categories | 13 |
| `timing_only` | per category (excluding unknown): present, circular mean clock time (sin, cos), first onset, last offset, number of bouts; plus total transitions | 73 |
| `totals_plus_timing` | both of the above | 86 |

Each baseline uses the same pipeline: standardize, then k-means (PCA available but off), fitted on train.
Absent-activity timing values are filled with the train mean over diaries that contain the activity, and
a `present` flag records the absence.

Not built yet: joint-latent sequence model and split model without invariance. Both need the VAE
(Checkpoints 3-4).

## What the evaluation can detect

- **Total-preserving transforms move timing features but never totals features.** A 30-minute shift
  moves timing features about 0.09 of a typical between-diary distance, a 2-hour shift about 0.37-0.40, and
  a block swap about 0.25. The totals features stay exactly the same in every case. So the evaluation can
  register changes in temporal organization when totals are fixed. Shifts wrap across 04:00, and that
  boundary effect is artificial.
- **Real diaries with near-identical totals still differ in timing.** For nearest-neighbour pairs within
  60 minutes of reassigned totals (179 pairs), timing distance is a median 0.59 of a random pair's
  distance. Within 120 minutes (740 pairs) it is 0.73. Timing clusters split these pairs more often than
  totals clusters do: at k=6, 66% vs 95% same-cluster within 120 minutes.
- **Totals explain little of when activities happen.** Ridge regression from totals predicts circular
  centre times with median validation R^2 0.03, and first/last times with about 0.06-0.10. Bout counts
  (0.42) and presence (0.33) are more predictable. Caveat: this model is linear, while presence is a
  deterministic but non-linear function of totals. A non-linear predictor would give a stricter test of
  "timing beyond totals" and is worth adding before Checkpoint 5.

## What the clusters look like

- **Cluster structure is weak.** Validation silhouette is at most 0.24 for totals and below 0.08 for
  anything with timing features. The groups partition a continuum and are not well-separated types.
  This is expected for daily schedules and matters for how archetypes are described later.
- **The k-selection rule picks k=2-3.** The rule: best silhouette with bootstrap ARI >= 0.8 and no
  validation cluster under 3%. Those clusters mostly split work days from non-work days. Stability drops
  to about 0.65-0.8 bootstrap ARI for k >= 4.
- **At the fixed comparison k=6** (added after seeing the k table; not a selected k), timing-aware
  clusters include:
  - standard daytime work (~22%, work centred ~12:00);
  - partial-work / errands days;
  - home-centred leisure days;
  - mornings with "other" activities (religious/volunteer, ~2 h);
  - out-and-about days with more travel and shopping;
  - a small (~2%) education-day group.
  These are descriptions of days, not of people.

## Decisions to revisit

- The k-selection rule and the 3% minimum cluster size were set before any results and produce a
  coarse k. Choosing k for the final analysis needs an explicit decision, for example a minimum stability
  plus interpretability, set before Checkpoint 5 and applied the same way to the VAE timing latents.
- Timing features are 73-dimensional and outweigh the 13 totals dimensions in `totals_plus_timing`
  after standardization. A block-weighted variant would compare the two information sources more fairly.
- The plots fold education, shopping/services, exercise, other and unknown into one gray band, so the
  education and "other" clusters are only distinguishable in the tables.
